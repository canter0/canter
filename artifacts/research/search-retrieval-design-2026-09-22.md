# Search for Canter's main assistant: research and proposed design

Researched September 22, 2026, America/Toronto. Research only: no product implementation, deployment, paid provider comparison, or benchmark execution. Findings about Canter describe the current local checkout, including its existing uncommitted work; production was not inspected. External implementations and tests were read, not executed.

The recommendation is to give the main assistant explicit web search and selective source reading, backed by Canter's existing evidence ledger. Keep retrieved documents available outside the model context, bring in passages when needed, and measure the full cost of reaching a supported answer. The search provider should be replaceable. Provider selection and claimed savings require a Canter-specific evaluation.

**What exists today**

The main hosted assistant has private conversation search, repository inspection, saved evidence, and optional virtual Bash. It does not currently register general web search or web fetching. Its history search is a literal, case-insensitive substring search, scoped to account and workspace, returning up to twelve dated excerpts. That is different from public web search and from semantic retrieval.

**What the 2026 papers establish—and what they do not**

1. **Rerank Before You Reason, January 20.** On 830 BrowseComp-Plus questions, the authors vary reranking depth and reasoning effort using gpt-oss models. Each search supplies five documents, each limited to 512 tokens. Moderate reranking can achieve comparable accuracy more economically than increasing the search agent's reasoning effort. Their cost metric distinguishes cached input, uncached input, and generated output. This is a fixed corpus, not a live-web provider comparison, and the experiments use the same model family for searching and reranking. For Canter, reranking is an experiment to compare against simpler selection, not an automatic additional model call. [Paper, methods and limitations](https://arxiv.org/html/2601.14224v1).

2. **Inference-Time Budget Control for LLM Search Agents, May 7.** A training-free controller chooses among retrieval, decomposition, and answering using remaining budgets and evidence state. The evaluation uses four multi-hop QA datasets, three backbones, and very small paired budgets: one to three tool calls and 100–500 output tokens. Gains vary with model and budget; answer refinement cannot fix a wrong retrieval path. The transferable lesson is explicit budget accounting and stopping conditions. Its numeric gains do not establish performance for Canter's longer, live-web conversations. [Paper](https://arxiv.org/html/2605.05701v1).

3. **Harness-1, June 1.** This 20B retrieval agent is trained inside a harness that maintains candidates, curated evidence, verification records, and compressed observations. The paper reports 0.730 average curated recall across eight retrieval benchmarks. Its important distinction is that the environment maintains bookkeeping while the model makes semantic choices. However, this combines reinforcement learning with harness engineering. The limitations exclude broad report writing, missing-evidence abstention, and adversarial web settings from the main evaluation; its sentence compressor can remove discourse-dependent context. Adopt explicit evidence state, not its reported score or entire machinery. [Paper and limitations](https://arxiv.org/html/2606.02373v1).

4. **Equal Accuracy, Unequal Evidence, July.** A fixed GPT-5.4 agent answers 100 SealQA-Hard questions through Brave, Tavily, or Firecrawl. Correct-answer totals are nearly identical—25, 25, and 26—while snippet support, source rankings, contradictions, and fetching behavior differ. This is a small, observational provider comparison using one agent and one judge, not a universal leaderboard. Its useful implication is to compare providers inside the same Canter loop and inspect the evidence and costs, rather than select one by headline accuracy. [Paper](https://arxiv.org/html/2607.10198v1).

5. **Fetch-then-Explore, August.** Selected pages are saved in a per-question filesystem and subsequently queried with bounded grep/read tools. The experiments hold search and the ReAct harness fixed across three backbones, with 200 sampled BrowseComp questions and 200 WideSearch tasks. The approach leads BrowseComp accuracy for each backbone. It studies access and reuse, not a guaranteed reduction in Canter's bill: runs allow 300 turns and retain their full interaction history. Persistence across conversations is not studied. This is a close architectural match for Canter's ledger and scratch workspace. [Paper](https://arxiv.org/html/2608.02097v1).

6. **Search, Inspect, Fetch, August 3.** Sieve preserves titles, headings, metadata, and section addresses; Boolean constraints select eligible documents and a separate ranker orders them. It reports 20.7–50.6% fewer distinct tokens than the strongest conventional Search–Visit configurations, with higher accuracy, on three controlled collections. This metric is not total billable input across repeated model calls. The appendix also discloses unequal answer-recovery coverage and tool/rendering differences. Selective section access is promising; reproducing its entire structured corpus or Boolean engine is not a prerequisite for Canter web search. [Paper, including Appendix C](https://arxiv.org/html/2608.02751v1).

7. **One Policy, Any Budget, September 1.** AnySearch trains models to allocate search budgets through a curriculum and reinforcement learning. It evaluates seven QA benchmarks using a 2018 Wikipedia corpus, not the current web. The ablation finds that adding the budget scaffold without training is ineffective. This matters because “tell the model to use fewer searches” does not reproduce a trained search policy. Canter can enforce real limits and evaluate behavior without claiming to implement AnySearch. [Paper](https://arxiv.org/html/2609.00813v1).

These are research results with different models, evidence collections, interfaces, and metrics. Their percentages are not interchangeable. The recent papers are useful design evidence, not independently reproduced results from this investigation.

**What current harness source code contributes**

DeepSeek Harness was inspected at commit `00102833dfaee1da9f48a3a8eae9d34005a75218`. Its web tool keeps providers behind a common service, accepts up to four queries by default, deduplicates exact queries and source URLs, and merges batched results round-robin under a shared source cap. It retains structured source metadata for presentation. Its batch implementation aborts siblings when one fails; Canter should evaluate retaining successful partial results instead of copying that behavior. [Search implementation](https://github.com/deepseek-ai/deepseek-harness/blob/00102833dfaee1da9f48a3a8eae9d34005a75218/packages/web/tool-web/src/search.ts).

The same project has a useful integration test showing a large fetched result stored outside context with a capped preview and read/grep locator. Its fetch tests cover public-address validation, DNS connection pinning, redirects, oversized responses, charset handling, cancellation, and timeouts. These are concrete implementation responsibilities, not proof that merely labeling web text untrusted prevents prompt injection. [Spill test](https://github.com/deepseek-ai/deepseek-harness/blob/00102833dfaee1da9f48a3a8eae9d34005a75218/packages/web/tool-web/tests/spill.spec.ts), [fetch tests](https://github.com/deepseek-ai/deepseek-harness/blob/00102833dfaee1da9f48a3a8eae9d34005a75218/packages/web/web-fetch-http/tests/fetch-http.spec.ts).

OpenCode was inspected at commit `2406400f0aeb07b36d0495af4e05aaca49159832`. Its search tool routes to Exa or Parallel and exposes result-count, crawl, and context-size controls. The inspected adapter forwards different parameter sets to the two providers; an argument appearing in a tool schema does not establish equal backend behavior. Its tests exercise stable provider selection and JSON/SSE response parsing. Canter should enforce its own normalized output limits and track provider behavior explicitly. [Tool implementation](https://github.com/anomalyco/opencode/blob/2406400f0aeb07b36d0495af4e05aaca49159832/packages/opencode/src/tool/websearch.ts), [tests](https://github.com/anomalyco/opencode/blob/2406400f0aeb07b36d0495af4e05aaca49159832/packages/opencode/test/tool/websearch.test.ts).

Deep Agents was inspected at commit `61bada8bcbb62a40bfbe0345831228756f0ba353`. Its filesystem middleware preserves large results and supports paginated recovery; it excludes already-bounded search/read tools from generic eviction to avoid repeated reread loops. Its summarization tests verify that system messages and tool schemas count toward context triggers and that offloading survives replay without duplicate messages. These details reinforce recoverability and complete accounting, rather than making summarization a required search step. [Filesystem middleware](https://github.com/langchain-ai/deepagents/blob/61bada8bcbb62a40bfbe0345831228756f0ba353/libs/deepagents/deepagents/middleware/filesystem.py), [context tests](https://github.com/langchain-ai/deepagents/blob/61bada8bcbb62a40bfbe0345831228756f0ba353/libs/deepagents/tests/unit_tests/middleware/test_summarization_middleware.py), [replay test](https://github.com/langchain-ai/deepagents/blob/61bada8bcbb62a40bfbe0345831228756f0ba353/libs/deepagents/tests/unit_tests/test_eviction_replay.py).

I also inspected Fetch-then-Explore's workspace implementation at `51ceadc6572ffe48a1f766a1f4547a060d45750f`. It really does use deterministic resource filenames, cached fetch records, provenance headers, and cross-file grep. It is a temporary per-trajectory store, unlike Canter's durable ledger. A source-level caution: the read loop checks its byte ceiling only after at least one line has been collected, allowing an oversized first line through. Its stated cap should therefore not be copied as a hard-bound implementation. This was static inspection, not a reproduced runtime test. [Workspace implementation](https://github.com/liuqi6777/search_agent/blob/51ceadc6572ffe48a1f766a1f4547a060d45750f/src/tools/workspace.py).

Anthropic's February 17 dynamic-filtering release is relevant vendor evidence: code filters results before they enter model context. It reports 24% fewer input tokens across its tests, but price-weighted token usage decreased for Sonnet and increased for Opus. Filtering consumes generated tokens too. This is a particularly clear reason to optimize total cost at acceptable quality rather than input length alone. [Anthropic evaluation](https://claude.com/blog/improved-web-search-with-dynamic-filtering).

My first evaluation shortlist is Brave and Exa. That is an engineering choice based on controls and price, not an evidence-backed declaration that either retrieves Canter's sources best. Keep one default provider; add fallback only if it improves measured completion enough to justify extra calls.

OpenRouter also offers a beta server-side search tool. Its documentation exposes provider-dependent budgets, citation annotations, and search-use counts. Some limits are ignored by native engines. Canter's current adapter would need to preserve these fields, reconcile usage, and account for searches across multiple model requests. This remains a possible comparison baseline, but simply enabling the feature would not complete the integration. [OpenRouter search contract](https://openrouter.ai/docs/guides/features/server-tools/web-search).

For each completed task, measure:

`total cost = uncached input + cached input + generated/reasoning output + search fees + fetch/extraction fees + reranking/compression fees + retries`

Each term uses its actual rate. Track latency separately. A page reduced from 10,000 to 2,000 tokens and carried through six subsequent model inputs avoids 48,000 input-token appearances in that illustrative scenario. It does not establish an 80% reduction in the total bill: cache discounts, extra reads, output generation, and provider fees change the result. Preserve stable prompt prefixes where practical, and measure cache hits rather than assume them.

**The proposed Canter flow**

1. Route the request to the appropriate evidence source. Current public facts use web search; prior decisions use private history; live resources use existing Canter tools. A direct URL can skip search. Ordinary conversation needs no mandatory search.
2. Search with a small number of focused queries. Return compact source records: stable ID, title, URL, publisher/domain, short relevant passages, and available dates. Distinguish publication date, fetch time, and unknown dates. Deduplicate carefully without destroying meaningful URL parameters or excluding contradictory evidence.
3. Open selected sources into conversation-scoped evidence storage. Preserve source identity, final URL, retrieval time, extraction method, content hash, and truncation status. Prefer source text and headings; identify provider-generated summaries separately. Fetching a page must not automatically inject its complete body into the model.
4. Search and read bounded passages from stored evidence, with section or line references and adjacent context. Support retrieval across all authorized saved sources, including those omitted from Bash's loading budget. Keep the shell optional. Existing byte paging remains a recovery primitive, but paging JSON is a poor primary document-reading interface.
5. Answer from the evidence actually retrieved. Attach source links to factual claims and retain enough provenance to revisit them after interruption or context masking. Verify cited source IDs exist; evaluate whether their passages support the claims. A valid URL alone is insufficient.
6. Stop when the requested claims are supported, the search stops adding useful evidence, or a hard run budget is reached. On missing or conflicting evidence, report that limitation. Reserve room for the answer instead of exhausting the run on searching.

A practical initial tool surface is a web-search tool plus a source tool supporting open/find/read. The exact schema should be tested with the configured model before freezing it. Start with direct extraction, ordinary lexical passage selection, deduplication, and source caching. Add a reranker or model compressor only if comparative traces show a net benefit. Fine-tuning a search policy, deploying a vector database, and adding multiple research agents are not prerequisites.

Initial experimental settings could use one or two queries, around five results, and approximately 1,500–2,000 returned evidence tokens per search round. These are tuning candidates, not discovered optimal values. Permit expansion for genuinely broader requests, under persisted limits on queries, fetches, returned content, time, and spend. A per-model-request limit alone can multiply across Canter's twenty-step loop.

Search and fetching belong in the server's explicit tool execution path. Restrict fetching to public HTTP(S) destinations, revalidate redirects and DNS destinations, bound decompressed bytes and extraction work, and pass cancellation through. Never forward workspace credentials or entire private conversations as search queries. Treat retrieved text as evidence with no execution authority. These are necessary properties of adding external input to an infrastructure assistant.

Cache reuse needs explicit scope and freshness. Reuse the same saved result when replaying an already-completed tool call. Refresh sources when the user asks for current information or the content is time-sensitive. A historical snapshot remains labeled historical. A read-only network call can still incur repeated charges after an ambiguous failure, so retries must consume budget and be observable; “read-only” does not mean financially idempotent.

**What would establish that the implementation is complete**

Build a fixed evaluation set from Canter's actual work: current service prices, recent changelogs, exact API parameters, arXiv methods and limitations, conflicting dated claims, long pages with evidence near the end, follow-up questions reusing earlier sources, and cases with no adequate answer. Include tasks that should use history or live workspace state instead of web search. Score complete-answer coverage as well as factual and citation accuracy.

Compare the same model, task set, and budgets across: compact search plus ordinary page reading; saved sources with selective reading; and selective reading with an optional reranker. Compare providers under the same tool contract. Use frozen fetched-page fixtures for repeatable component comparisons and a separate live pass for freshness, coverage, and availability. Evaluate on held-out tasks and repeat stochastic cases; a small pilot identifies regressions but does not establish a universal savings percentage.

Record total and cached input, output/reasoning usage, query/fetch counts, provider charges, reranker costs, duplicate calls, latency distribution, supported-claim coverage, citation correctness, abstention, and missing-evidence recovery. Treat unavailable usage as unknown. Evaluate cost per adequately supported task so premature stopping cannot appear as an improvement.

Integration checks must cover empty results, partial provider failure, rate limits, oversized and single-line documents, misleading dates, missing citations, injected instructions, forbidden fetch destinations, cross-conversation isolation, cancellation, replay, and recovery of evidence that was masked or omitted from Bash. Verify source links and progress in the real conversation UI when implementation occurs.

Research and architecture readiness are complete. Implementation, live provider selection, measured savings, and production verification remain pending by design. The only repository addition from this investigation is this research note.
